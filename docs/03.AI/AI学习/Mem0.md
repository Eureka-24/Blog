# mem0 记忆引擎源码剖析：当 AI 学会了"记事儿"

> **一篇关于 mem0 V3 批处理管道的技术博客**  
> 原文: `mem0/memory/main.py` · 3223 行 · 同步/异步双引擎

---

## 前言

你有没有想过，AI 是怎么"记住"你的？不是对话窗口里的上下文，而是跨会话、跨设备的长期记忆——那些你提过的喜好、聊过的计划、说过的小事。

**[mem0](https://github.com/mem0ai/mem0)** 正是干这个的开源库。它给大语言模型配上了一个"记忆皮层"：能存、能搜、能更新、能遗忘，而且每一步都有精巧的设计。

最近花了些时间深入啃了它的核心源码，发现里面藏着一个相当成熟的 **V3 批处理管道**。这篇文章就来拆解它的四板斧：**增、删、查、改**。

---

## 一、先看全景：记忆引擎长什么样

整个引擎的核心在 `mem0/memory/main.py`，约 3223 行代码，封装了两个类：

```
Memory          → 同步版本，直接调用
AsyncMemory     → 异步版本，通过 asyncio.to_thread() 委派到线程池
```

它们的公共 API 完全一致，背后的依赖链是：

```
你的代码 → Memory 类 → LLM (提取事实)
                     → Embedding 模型 (文本→向量)
                     → 向量数据库 (语义索引)
                     → SQLite (历史审计)
                     → Entity Store (实体图谱)
                     → Reranker (重排序, 可选)
```

每个组件都是可插拔的 —— LLM 可以用 OpenAI 也可以用 Ollama，向量库可以选 Qdrant 也可以选 Chroma 甚至 FAISS。

## 二、加记忆 (Add)：八阶段流水线

加记忆是最复杂的操作，尤其当 `infer=True` 时，引擎会启动一个 **8 阶段批处理管道**。

### Phase 0：先摸摸底

引擎做的第一件事是翻旧账——去 SQLite 里拉出最近 10 条对话，拼接成上下文。这样 LLM 做提取时就有"前情提要"了。

### Phase 1：搜一搜已有的

把当前消息编码成向量，在向量库里搜 10 条最相关的现有记忆。注意一个小细节：**搜出来的 UUID 会被映射成整数 ID**（"0"、"1"、"2"...）才传给 LLM。为啥？因为 LLM 容易"幻觉"出根本不存在的 UUID，用整数 ID 杜绝这个坑。

### Phase 2：LLM 一次搞定

这是最精髓的一步。**一次 LLM 调用**，同时完成"哪些该加、哪些该改、哪些该删"的决策。

传给 LLM 的 prompt 精心设计了多个输入区：

```
Summary: 用户画像摘要
Existing Memories: 现有的记忆列表 (用整数 ID)
New Messages: 当前对话
Last k Messages: 最近的历史消息
Observation Date: 对话发生日期
Custom Instructions: 用户自定义规则
```

LLM 输出 JSON：

```json
{
  "memory": [
    {"text": "用户喜欢打网球，每周六早上和朋友去球场", "attributed_to": "user"},
    {"text": "用户被推荐了威尔逊的网球拍", "attributed_to": "assistant"}
  ]
}
```

你可能会问：一次调用够精准吗？项目的答案是——**宁可漏判也不要多判**。一条多余的记忆远没有一条缺失的记忆代价大，下游有哈希去重兜底。

### Phase 3：批量向量化

提取出的文本一次性批量生成 embedding，而不是一条一条来。如果批量接口失败，优雅降级为逐条嵌入。

### Phase 4 + 5：哈希去重保幂等

每条文本算一个 MD5 哈希，跟库里已有的以及本次批处理中见过的哈希比对，重复的直接跳过。

这是整个系统的**幂等性保障**：同样的话说多少遍，记忆也只有一份。

### Phase 6：落盘

向量批量插入向量库，历史批量写入 SQLite。任何一步失败都有逐条回退的兜底。

### Phase 7：实体链接 (最复杂的环节)

这个阶段开了一个**独立的实体库**（`{collection_name}_entities`），专门做实体识别和关联。

大概逻辑是这样：

```
从新记忆中提取实体 (人名、地名、作品名...)
  → 全局去重（同一个实体只处理一次）
  → 批量生成实体向量
  → 在实体库里搜索相似实体 (相似度 >= 0.95)
    ├─ 找到了 → 把当前记忆 ID 追加到已有实体的关联列表
    └─ 没找到 → 创建新实体，关联当前记忆
```

每个实体的记录长这样：

```json
{
  "data": "John",
  "entity_type": "person",
  "linked_memory_ids": ["记忆A的UUID", "记忆B的UUID"]
}
```

这套实体索引在搜索时至关重要——匹配到同名实体的记忆会获得额外的**分数加权**（详见后文）。

### Phase 8：收尾

保存原始消息供后续上下文使用，发送遥测事件，返回结果。

## 三、查记忆 (Search)：三重信号的交响乐

搜索是引擎中最有技术含量的读操作。它融合了**三种信号**：

### 信号一：语义向量

老本行——把查询编码成向量，在向量库里做近似搜索。

### 信号二：BM25 关键词

查询文本经过**词形还原**（running → run），做经典的关键词匹配。原始 BM25 分数通过 Sigmoid 函数归一化到 [0, 1]，Sigmoid 的参数根据查询长度自适应：

```
≤3 个词: (midpoint=5.0,  steepness=0.7)
≤6 个词: (7.0, 0.6)
≤9 个词: (9.0, 0.5)
>15 个词: (12.0, 0.5)
```

短查询需要更陡峭的曲线，长查询则更平缓。

### 信号三：实体提升

查询中的实体被提取出来后，去实体库里搜一波。命中的实体关联了一堆记忆 ID，这些记忆获得额外加分。

加分公式：

```
boost = 实体相似度 × 0.5 × 衰减因子

其中衰减因子 = 1 / (1 + 0.001 × (关联记忆数 - 1)²)
```

这个衰减设计非常实用：一个实体如果关联了 5000 条记忆，它的提升权重会被压制到几乎为零，防止"万能实体"过度影响排序。

### 最终融合

```
combined = (semantic + bm25 + entity_boost) / max_possible
```

`max_possible` 根据当前启用了哪些信号动态计算，确保分数落在 [0, 1]：

```
仅语义:               max = 1.0
语义 + BM25:          max = 2.0
语义 + BM25 + 实体:   max = 2.5
```

还有一个细节：**先过语义阈值，再融合**——语义分不到 threshold 的直接淘汰，BM25 和实体加成分救不回来。这是为了防止完全无关的内容被关键词误抬上来。

### 可选：重排序

如果配置了 reranker（比如 Cohere），最终结果还会被重排序引擎再排一次。

## 四、改记忆 (Update)：温柔地"动刀"

更新操作比想象中要谨慎，因为它要保证**不丢失归属信息**。

核心逻辑在 `_update_memory()`：

```
1. 从向量库拿到旧记忆
2. 旧值存档 (用于审计)
3. 构建新数据:
   data = 新文本
   hash = MD5(新文本)
   created_at = 保留旧时间  ← 创建时间永远不变
   updated_at = 当前时间    ← 修改时间标记
4. session 标识符继承:
   如果新 metadata 没传 user_id → 从旧记忆继承
   同理 agent_id、run_id、actor_id、role 都继承
5. 更新向量库
6. 写入历史 (记录旧值→新值)
7. 更新实体索引:
   先解除旧文本的实体关联 → 再从新文本提取实体重新关联
```

第 7 步保证了记忆文本变了，实体索引也同步更新，不会留下脏数据。

## 五、删记忆 (Delete)：不只是删除

删一条记忆分三步：

```
1. 从向量库里物理删除 (vector_store.delete)
2. 写入审计历史，标记 is_deleted=1
   (保留"删除前的值"和"删除后的值=None"的完整记录)
3. 从实体索引中解除关联:
   遍历所有实体，移除该记忆 ID
   如果实体关联列表空了 → 实体也删掉
```

有意思的是**批量删除 `delete_all()`**：异步版本用了 `asyncio.gather()` 并发执行所有删除，性能比同步版本好一个量级。

而 **`reset()`** 更彻底：删库、删表、重建客户端，一切归零。

## 六、那些"看不见"的设计

读源码的过程中，有几个设计特别值得一说。

### 6.1 会话隔离：三口之家

每条记忆都通过 `user_id`、`agent_id`、`run_id` 三重标识来隔离。你可以：

- 只查某个用户的记忆 (`user_id`)
- 只查某个 AI 助手的记忆 (`agent_id`)
- 只查某次运行的记忆 (`run_id`)
- 或者组合查询

这在多租户场景下极其重要。

### 6.2 Prompt 工程：千行级系统提示

项目里的 `prompts.py` 有 **1063 行**。其中 V3 的 `ADDITIVE_EXTRACTION_PROMPT` 包含了详尽到令人发指的规则：

- 从哪些角色提取 ("别漏了 assistant 给出的具体推荐")
- 哪些不提取 ("'听起来不错'这种废话跳过")
- 时间锚定 ("'上周'→ 对观察日期来说的上周，不是今天")
- 复数主题 ("用户问了餐厅推荐也聊了养猫——两个都要记")
- 多说话人场景 ("'John: ...' 和 'Maria: ...' 是两个不同的人，各自的信息都得提取")

这大概是我见过最卷的 prompt 了。

### 6.3 优雅降级：到处是兜底

读下来有个强烈感受：代码里几乎每处可能失败的地方都有兜底。

- 批量 embedding 失败 → 逐条重试
- 批量向量插入失败 → 逐条重试
- Entity store 整个挂掉 → 打日志，不影响主流程
- 配置 deepcopy 失败 → 基于 dict 克隆

所有非关键路径的错误都不扩散。

### 6.4 安全处理

配置文件中的 `api_key`、`secret`、`password` 等敏感字段在克隆时会自动置空，而 `http_auth`、`ssl_context` 这类运行时连接对象则被保留。

## 写在最后

读 mem0 的源码有一种感觉：作者不是在写一个库，而是在打磨一个**记忆操作系统**。从批处理管道到三重信号搜索，从实体索引到衰减公式，每一处都不是拍脑袋的设计。

如果说有什么遗憾的话，文件确实太长了——3223 行的 `main.py` 如果能拆分成更细的模块会更好维护。但代码质量本身是过硬的：类型提示完善、错误处理到位、异步版本考虑周全。

对于想做 AI 记忆功能的人来说，mem0 提供了一个相当成熟的参考实现。就算不用它，光是读完源码也能学到很多关于** RAG 混合检索**、**LLM 批处理提取**和**实体索引**的实战技巧。
