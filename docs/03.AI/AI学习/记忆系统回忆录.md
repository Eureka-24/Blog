# 记忆系统深度复盘：Agent 应该记住什么、怎么记住、记住多久？

------

## 摘要

在 AI Agent 系统中，记忆是实现智能行为的核心基础。然而，大多数团队在设计记忆系统时，往往只关注 "能不能存" 和 "能不能搜"，却忽略了更本质的问题：**应该记住什么、怎么记住、记住多久**。

本文记录了企业级 Agent 记忆系统设计过程中的完整思考路径。从对比行业标杆 Letta 和 Mem0 开始，通过连续五个核心问题层层深入，最终放弃了看似先进的 Core Memory 自进化架构，选择了 "静态常驻上下文 + 被动检索记忆" 的混合模式。

这不是一篇关于向量检索实现的技术教程，而是一篇关于**架构取舍**的深度思考。它探讨了一个所有 AI 开发者都必须面对的核心问题：**在当前技术阶段，到底应该信任 Agent 到什么程度？**

------

## 一、序幕：功能齐全的 "无魂系统"

一切从一个看似简单的问题开始。

当打开项目，看到 `src/main/java/com/eagent/memory/` 目录下那一排排整齐的类文件时，第一反应是欣慰：记忆系统已经完成了。

这套系统拥有当下所有主流的组件：

- `MemoryItem` —— 标准化记忆数据单元
- `MemoryLog` —— 全链路事件日志与审计系统
- `MemoryManager` —— 统一的记忆操作入口
- `VectorStore`(Qdrant) —— 高性能稠密向量存储
- `DbStore`(H2) —— 支持事件溯源的关系型存储
- `Embedder`(Ollama) —— 本地可部署的文本嵌入服务
- `Extractor`(LLM) —— 基于大模型的事实提取器
- `SparseVectorizer` —— 基于 BM25 的稀疏向量生成器

系统甚至实现了业界公认效果最好的**稠密 + 稀疏混合检索**和**RRF (Reciprocal Rank Fusion) 结果融合算法**。从功能清单上看，这套系统无懈可击：能存、能搜、能提取、能过滤、能去重。

但这套系统始终缺少灵魂。它有所有的组件，却没有清晰的设计哲学和使用原则。它就像一个装满了工具的工具箱，却没有明确的使用指南：**什么时候该用哪个工具？哪些工具其实根本不需要？**

于是，新功能开发被暂停，一场关于记忆本质的深度追问正式开始。

------

## 二、第一问：行业标杆的记忆系统是如何设计的？

在设计任何系统之前，先研究行业内最优秀的方案，是技术团队的基本准则。本文选择了两个最具代表性的项目进行深入分析：Letta (原 MemGPT) 代表了生产级 Agent 框架的最高水平，而 Mem0 则代表了轻量级记忆库的最佳实践。

### 2.1 Letta 的三层记忆架构

Letta 由 UC Berkeley 开发，其核心设计目标是突破 LLM 的上下文窗口限制，让 Agent 能够拥有 "无限长" 的记忆。它的三层记忆架构直接借鉴了人类的记忆模型：

```
Core Memory（核心记忆）
  → 始终驻留在 LLM 上下文窗口中
  → 结构化 Block 设计：label + value + limit + read_only + version
  → 渲染为 XML 格式注入 system prompt
  → Agent 通过专用工具编辑（replace / insert / rethink / patch）

Archival Memory（归档记忆）
  → 外部语义存储（支持 pgvector / Turbopuffer 等多种后端）
  → 基本单元为 Passage(text + embedding + tags + metadata)
  → 按需调用 search() 接口召回

Recall Memory（回忆记忆）
  → 完整的对话历史记录
  → 支持混合检索（全文匹配 + 语义相似度）
  → 用于还原完整的对话上下文
```

Letta 的设计哲学非常清晰：**将信息按重要性分层，最重要的信息永远带在身上，次要信息存在外部存储，需要的时候再去查询。**

### 2.2 Mem0 的七阶段流水线

Mem0 是一个开源的轻量级记忆库，专注于为 LLM 应用提供开箱即用的记忆能力。它的核心创新在于将记忆的生成过程标准化为一个七阶段的自动化流水线：

```
Phase 0: 上下文收集（默认获取最近 10 条消息）
Phase 1: 已有记忆检索（基于嵌入向量的相似度搜索）
Phase 2: LLM 事实提取（单次调用，结构化 JSON 输出）
Phase 3: 批量嵌入（Batch Embedding，提升处理效率）
Phase 4: 逐条处理 + 哈希去重（避免重复记忆）
Phase 5: 批量持久化（减少数据库 IO 次数）
Phase 6: 历史记录写入（完整的操作审计）
Phase 7: 实体提取与链接（构建知识图谱的基础）
```

Mem0 的设计哲学是：**记忆应该是一个自动的过程，不应该让 Agent 或者开发者操心。** 开发者只需要调用简单的 `add()` 和 `search()` 接口，所有复杂的逻辑都在流水线内部完成。

### 2.3 现有系统现状

对比之下，当时的系统流程显得简单而粗糙：

```
用户提问 → 混合检索(dense + sparse) → RRF 结果融合 → 纯文本拼接 → 注入 context
```

系统有检索，但没有分层；有提取，但没有流水线；有存储，但没有管理策略。这套系统能够工作，但它的行为是不可预测的 —— 无法预知它会记住什么、会忘记什么、什么时候会出错。

------

## 三、第二问：Core Memory 与检索注入的本质区别是什么？

> **核心问题**：Letta 的 Core Memory 和每次查询时进行的检索注入，不都是在给 LLM 提供背景事实吗？它们之间的本质区别到底是什么？

这个问题困扰了技术团队很长时间。直观上，两者的目标完全一致 —— 为 LLM 提供回答问题所需的上下文信息。但直觉表明，它们之间一定存在着根本性的差异。

直到将两者的所有特性放在一起进行了详细的对比：

|  特性维度  |           检索注入模式           |       Letta Core Memory 模式       |
| :--------: | :------------------------------: | :--------------------------------: |
|  加载时机  |      每次用户查询时动态加载      |       Agent 启动时一次性加载       |
| 内容一致性 |       每次查询结果可能不同       |      始终一致（除非主动编辑）      |
|  依赖关系  |    依赖嵌入模型质量和检索算法    |         不依赖任何外部系统         |
|  访问延迟  | 50-200ms（取决于向量数据库性能） |               零延迟               |
| Token 消耗 |    按需消耗（只注入相关信息）    | 每轮对话都消耗（即使内容完全不变） |
| 结果确定性 | 概率性（召回率和准确率 < 100%）  |             100% 确定              |
|  错误恢复  |  自愈性（新信息自动覆盖旧信息）  |     不可自愈（错误会持续存在）     |

当这个对比表格完成的那一刻，答案变得清晰起来：

> **检索注入是 "去图书馆查资料"，而 Core Memory 是 "随身笔记本"。**

图书馆藏书丰富，但每次能查到什么取决于提问方式；随身笔记本虽然容量有限，但永远在手边，翻开就能看到记录的内容。这就是它们最核心的区别。

------

## 四、第三问：既然有检索，为什么还需要 Core Memory？

> **核心问题**：Letta 也有强大的 Archival Memory 检索系统，现有系统也有。既然检索的开销已经不可避免，Core Memory 存在的意义到底是什么？更何况它还存在容易保存错误记忆、难以更新的致命缺陷。

这个问题非常尖锐，因为它直接挑战了 Letta 最核心的设计选择。如果已经有了能够召回任意信息的检索系统，为什么还要牺牲宝贵的上下文窗口和 Token 来维护一个 Core Memory 呢？

### 4.1 Core Memory 的不可替代性

经过深入分析，研究表明 Core Memory 解决的是检索系统的**本质缺陷**—— 检索是一个概率系统，它永远无法保证 100% 的召回率和准确率。

在以下三个场景中，Core Memory 的价值是不可替代的：

**场景一：代词指代与隐式信息**

> 用户说："帮我按那个风格写代码"
>
> 这里的 "那个" 是一个没有任何语义信息的代词。基于语义相似度的检索系统几乎不可能召回 "用户喜欢函数式编程风格、每个函数不超过 20 行、必须有完整的类型注解" 这条记忆。

**场景二：关键安全与合规规则**

> 系统中有一条绝对规则："永远不要输出任何 API Key 和数据库密码"
>
> 当用户问 "帮我看看支付接口的配置有什么问题" 时，这条安全规则能排在检索结果的前几位吗？不一定。但如果它被遗漏，后果将是灾难性的。

**场景三：高确定性要求的场景**

> 在金融和医疗等领域，Agent 的每一个回答都必须符合严格的合规要求。
>
> 检索系统返回的结果每次可能不同，但合规规则必须 100% 被遵守，不能有任何侥幸。

在这些场景下，概率性的检索是不可接受的。需要一种机制，能够保证某些信息**永远**出现在 LLM 的上下文中，无论用户问什么问题。这就是 Core Memory 存在的根本原因。

### 4.2 Core Memory 的致命缺陷

然而，Core Memory 也有一个几乎无法解决的致命缺陷：**由 Agent 自维护的记忆是不可靠的。**

在实际测试中，发现了以下典型问题：

1. **更新不及时**：当用户的偏好发生变化时（"我以前喜欢 Python，现在更喜欢 Rust"），Agent 经常会忘记更新 Core Memory
2. **错误写入**：Agent 可能会误解用户的意思，将错误的信息写入 Core Memory
3. **信息冲突**：Core Memory 中可能会存在相互矛盾的信息，导致 Agent 行为混乱
4. **无法自动删除**：过时的信息会一直留在 Core Memory 中，占用宝贵的上下文窗口

而在检索注入模式下，这些问题在很大程度上是 "自愈" 的：

- 新消息会自动生成新的嵌入向量
- 新的嵌入向量会优先匹配新的查询
- 旧信息虽然还在数据库中，但不会被检索到
- 错误的记忆只会影响少数几次查询，而不是每一轮对话

因此，Core Memory 的选择从来不是一个技术问题，而是一个**产品层面的权衡**：

> 是愿意为了 100% 的确定性，接受 Core Memory 带来的 Token 成本和不可靠性？还是愿意为了自愈性和效率，接受检索系统的概率性缺陷？

------

## 五、第四问：Core Memory 本质上就是可编辑的 CLAUDE.md 吗？

> **核心问题**：当深入分析 Core Memory 的工作原理时，一个惊人的类比浮现出来：Core Memory 不就是 Claude Code 中的 CLAUDE.md 吗？唯一的区别只是谁拥有编辑权。

这个类比揭示了 Core Memory 的本质，也让其风险得到了更深刻的认识。



|   特性   |     Claude Code 的 CLAUDE.md      |        Letta 的 Core Memory         |
| :------: | :-------------------------------: | :---------------------------------: |
|   载体   |   项目根目录下的 Markdown 文件    |      内存中的结构化 Block 对象      |
|   内容   |   开发者手写的项目规则和上下文    |   Agent 自动积累的用户信息和偏好    |
|  编辑权  |        只有开发者可以编辑         |     Agent 自己通过工具调用编辑      |
| 编辑方式 |        手动修改文件并保存         | memory_replace /insert/rethink 工具 |
| 生效时机 |          下次对话开始时           |          下一轮 LLM 推理时          |
|  可见性  | 始终出现在 system prompt 的最前面 |  始终出现在 <memory_blocks> 标签中  |

是的，它们几乎完全一样。唯一的区别只有一个：**谁有编辑权**。

- **CLAUDE.md 模式**：开发者写，Agent 读，Agent 不能改。安全、可控、可预测，但需要手动维护。
- **Core Memory 模式**：Agent 自己写、自己读、自己改。自适应、无需人工干预，但可能写坏。

团队内部进行了一次调查：如果有一天早上打开电脑，发现 CLAUDE.md 里的内容被 Claude 自己改了，会是什么感觉？

所有人的答案都是一致的：恐慌。

CLAUDE.md 之所以成为 Claude Code 最成功的设计之一，正是因为它将控制权完全交给了开发者。开发者可以精确地控制 Agent 知道什么、遵守什么规则、以什么方式工作。这对于企业级应用来说至关重要。

而 Core Memory 将编辑权交给了 Agent，这在带来自主性的同时，也引入了不可控性。在当前 LLM 还会频繁产生幻觉的技术阶段，这种不可控性是无法接受的。

------

## 六、第五问：到底应该做什么、不做什么？

经过四轮深入的追问，迷雾终于散去，方向变得清晰。最终做出了一个艰难但坚定的决定：**放弃 Core Memory 自进化架构，坚持 "静态常驻上下文 + 被动检索记忆" 的混合模式。**

### 6.1 决定放弃的特性

|         放弃的特性         |                          核心理由                           |
| :------------------------: | :---------------------------------------------------------: |
| **Core Memory Block 系统** |  Agent 自维护容易出错，每轮对话浪费 Token，且无法有效更新   |
|  **Agent 自进化记忆能力**  | 不可控，等价于让 Agent 自己修改系统配置文件，风险远大于收益 |
|  **复杂的实体提取与链接**  |   实现复杂度极高，且在当前场景下收益不明确，属于过度设计    |
| **Git 风格的记忆版本控制** |           增加了系统的复杂性，而实际使用频率极低            |

### 6.2 决定坚持的核心设计

|          坚持的特性          |                      核心理由                      |
| :--------------------------: | :------------------------------------------------: |
| **CLAUDE.md 风格的静态文件** |  开发者完全可控的常驻上下文，安全、可靠、不改不丢  |
|    **基于检索的归档记忆**    | 自愈性强，按需消耗 Token，能够处理无限量的历史信息 |
|  **LLM 驱动的隐式记忆提取**  | 无需 Agent 手动调用工具，记忆的生成和更新自动完成  |
| **完整的事件日志与审计系统** |  支持问题排查和行为回溯，满足企业级应用的合规要求  |

### 6.3 需要重点改进的方向

|           改进项           | 优先级 |                           预期收益                           |
| :------------------------: | :----: | :----------------------------------------------------------: |
|   CLAUDE.md 静态文件支持   |  最高  |      让常驻信息可配置，无需修改代码即可调整 Agent 行为       |
|     检索结果结构化注入     |  最高  | 将检索结果格式化为包含 ID、时间、置信度和来源的结构化对象，让 LLM 能够更好地评估记忆的可靠性 |
| LLM Extractor 记忆更新机制 |  最高  |  设计基于时间戳和语义相似度的冲突解决策略，自动标记过期记忆  |
|     时间范围与权重过滤     |   中   |             优先返回近期记忆，减少过时信息的干扰             |
|      RRF 融合参数调优      |   中   |        提升混合检索的排序质量，让更相关的记忆排在前面        |
|  SparseVectorizer 持久化   |   中   |       解决重启后 IDF 矩阵丢失导致的检索结果不一致问题        |

### 6.4 最终确立的架构原则

基于上述分析，确立了四条核心架构原则，作为未来所有记忆系统开发的指导方针：

1. **记忆是被动检索的，不是主动注入的**

   每轮查询只通过 search () 获取相关信息，不强制携带所有记忆，避免上下文窗口被不必要的信息占用。

2. **记忆是隐式管理的，不是显式编辑的**

   Agent 不直接调用任何记忆编辑工具，记忆的增删改全由 LLM Extraction 自动完成。

3. **常驻信息通过文件配置，不通过记忆系统**

   CLAUDE.md 作为 system prompt 的固定部分，这部分信息永远不由 Agent 改变。

4. **检索质量是记忆系统的生命线**

   所有的资源投入都应该围绕改善 search () 结果展开。

------

## 七、尾声：一个关于信任的命题

回头看，整个讨论其实围绕着一个所有 AI 开发者都必须面对的核心问题：

**在当前的技术阶段，应该信任 Agent 到什么程度？**

- 如果信任它能够准确地判断什么信息重要、什么信息不重要，能够正确地更新自己的记忆，不会犯错误 → 那么 Core Memory 自进化架构是合适的选择
- 如果认为 Agent 应该像一个优秀的助理，能够快速地从海量资料中找到需要的信息，但关键的规则和控制权应该掌握在人类手中 → 那么 "静态常驻上下文 + 被动检索记忆" 的混合模式是更优的选择

没有绝对正确的答案，只有适合不同场景的取舍。

最终选择了后者。不是因为 Core Memory 不好，而是因为目标场景是企业级内部工具。在这个场景下，**可控性和可靠性**远比自主性和智能化更重要。不能接受 Agent 因为记忆错误而产生的任何不可预测行为。

在 AI 技术飞速发展的今天，很容易被各种 "先进" 和 "智能" 的特性所诱惑。总想让 Agent 更像人，拥有自主学习和进化的能力。但有时候，**少即是多**。

> 好的系统设计不是做加法，把所有能想到的特性都加上。
>
> 好的系统设计是做减法，知道什么东西不应该做，然后坚决地砍掉它。

## 八、核心收获与思考

1. **记忆系统的本质是信息分层**：将信息分成 "永远需要的" 和 "可能需要的" 两类，分别用不同的方式处理，这是所有优秀记忆系统的共同特征。
2. **Core Memory = 可编辑的 CLAUDE.md**：理解了这个类比，就理解了 Core Memory 的本质和它的所有优缺点。
3. **信任是所有架构决策的基础**：对 Agent 的信任程度，决定了系统架构的选择。在当前技术阶段，保持谨慎是明智的选择。
4. **检索质量 > 一切花哨特性**：如果检索不准，再复杂的记忆系统也没有用。把资源投入到提升检索质量上，永远是最高效的选择。
5. **Token 成本是不可忽视的约束**：Core Memory 每轮都消耗 Token，对于高并发应用来说，这会带来巨大的成本负担。被动检索模式可以显著降低 Token 消耗。
6. **没有通用的架构**：不同的应用场景有不同的需求。企业级应用更看重可控性和可靠性，消费级应用可能更看重自主性和智能化。不要盲目跟风行业标杆。
