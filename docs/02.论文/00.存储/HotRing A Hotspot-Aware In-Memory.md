# HotRing: A Hotspot-Aware In-Memory Key-Value Store 论文总结

[论文链接](https://www.usenix.org/conference/fast20/presentation/chen-jiqiang)

## 一、研究背景与问题提出

内存键值存储（Key-Value Store, KVS）如 RocksDB、LevelDB 等被广泛应用于热点缓存场景，但在实际业务中，数据访问的 “热点倾斜” 问题日益突出 —— 少数热点数据占据了绝大多数访问请求，导致传统 KVS 在这类高度倾斜的工作负载下性能显著下降、可靠性降低。

核心症结在于传统 KVS 的设计逻辑：所有数据被 “无差别对待”，未针对热点数据的访问特征做针对性优化。以哈希索引为例，热点数据与非热点数据混合存储在同一哈希冲突链中，若热点数据出现在冲突链的靠后位置，会大幅增加查询时的遍历长度，直接拉高访问延迟，成为性能瓶颈。

![image-20260505102317536](https://cdn.jsdelivr.net/gh/Eureka-24/img@main/img/20260508204829178.png)

为解决这一问题，HotRing 提出核心设计理念：**感知 KVS 中的热点数据，通过主动的热点迁移和高效的并发访问控制，缩短热点数据的访问路径，提升整体服务能力**。

## 二、核心设计方案

### 2.1 基础数据结构：有序哈希冲突环

![image-20260505135949284](https://cdn.jsdelivr.net/gh/Eureka-24/img@main/img/20260508204831748.png)

HotRing 摒弃了传统的线性哈希冲突链，设计了有序的哈希冲突环（Hash Conflict Ring），并对长键做结构化拆分：将原密钥（Key）切分为 “主 Key + 标签（Tag）” 的组合形式。冲突环的核心特征是支持 “热点头指针（Hot Head）” 的动态移动 —— 通过将热点头指针指向访问频率最高的节点，让热点数据始终处于冲突环的最优访问位置。

### 2.2 热点检测机制

HotRing 设计了轻量且高效的热点检测策略，核心目标是精准识别热点数据并动态调整热点头指针，分为两种核心模式：

#### （1）随机移动检测

设置固定检测周期 R：每累计 R 次访问请求时，触发一次热点验证 —— 若第 R 次访问的是当前热点头指向的节点，则判定热点未偏移，不移动头指针；若访问的是非热点头节点，则将热点头指针直接移动至该访问节点，快速响应临时热点变化。

#### （2）统计采样检测

<img src="https://cdn.jsdelivr.net/gh/Eureka-24/img@main/img/20260508204838595.png" alt="image-20260505162618985" style="zoom: 67%;" />

为解决随机移动的 “瞬时性” 问题，统计采样检测实现了更精准的热点判定：

1. 触发逻辑：同样以 R 次访问为周期，若第 R 次访问非当前热点头节点，则标记 “Active” 位开启热点调整阶段；
2. 计数阶段：Active 置位后，全局访问计数器和各节点的独立访问计数器开始统计周期内的访问频次；
3. 计算与调整：采样周期结束后，重置 Active 位（确保后续计算由单线程执行，避免并发冲突），基于各节点的访问频率计算 “访问收益期望值”，将热点头指针移动至收益最大的节点，实现热点的精准锚定。

##### 特殊场景的热点适配

- **写密集型热点的 RCU 适配**：读 - 复制 - 更新（RCU）是 HotRing 的核心更新机制，但在写密集场景下，直接遍历冲突环更新热点头会引入额外开销。为此优化为：不直接遍历环，而是递增目标节点 “前一项” 的计数器，间接完成热点统计，避免遍历开销。

- 热点继承机制

  ：针对热点头节点的更新 / 删除操作做特殊处理，保证热点访问的连续性：

  - 头部节点 RCU 更新时，热点头指针直接指向更新后的新版本节点；
  - 头部节点删除时，热点头指针无缝切换至冲突环的下一个节点。

  

### 2.3 无锁并发操作设计

高并发场景下，锁机制会引入显著的时延和竞争开销，HotRing 基于 CAS（Compare-And-Swap）原子操作实现全链路无锁并发控制，同时通过 “Occupied 位” 解决并发冲突问题，核心操作设计如下：

|             操作类型             |                         核心实现逻辑                         |                   并发冲突解决                    |
| :------------------------------: | :----------------------------------------------------------: | :-----------------------------------------------: |
|               插入               | 通过 CAS 原子操作修改节点的 “下一项” 指针，保证同一时刻仅一个线程插入成功 |          无额外冲突，CAS 天然保证原子性           |
|               更新               | 1. 数据小于 8 字节：原地直接更新；2. 数据大于 8 字节：采用 RCU 机制；3. 冲突场景：若同时发生 “节点 B 更新为 B'” 和 “末尾插入节点 C”，先将 B 的 Occupied 位置位，阻塞 C 的插入 CAS 操作，待 RCU 更新完成后再释放，避免 C 丢失 | 利用 Occupied 位做并发阻塞，保证 RCU 更新的原子性 |
|               删除               | 先将待删除节点的 Occupied 位置位（标记为 “不可操作”），再执行删除流程 |       防止删除操作与插入 / 更新操作并发冲突       |
| 头指针操作（移动 / 更新 / 删除） | 先将新目标节点的 “前一项” Occupied 位置位，再通过 CAS 移动头指针 |    避免头指针变更与其他操作并发导致的链路断裂     |
|         重哈希（桶扩展）         | 利用 Key-Tag 拆分特性，将 Tag 的最高位合并至 Key 中，实现哈希桶的无损扩展；原冲突环可平滑拆分为两个新哈希环，无需全量重哈希![image-20260505203728874](https://cdn.jsdelivr.net/gh/Eureka-24/img@main/img/20260508204854161.png) |     无锁化扩展，保证扩展过程中读写操作不中断      |

## 三、核心创新与价值

HotRing 的核心创新在于将 “热点感知” 深度融入内存 KVS 的底层设计：

1. 从数据结构层面，用 “有序冲突环 + 动态热点头” 替代传统冲突链，从根本上缩短热点数据访问路径；
2. 从检测机制层面，兼顾 “快速响应”（随机移动）和 “精准判定”（统计采样），适配不同类型的热点特征；
3. 从并发控制层面，基于 CAS + Occupied 位 + RCU 的组合策略，实现全场景无锁化操作，在高并发下既保证性能，又避免数据一致性问题；
4. 从可扩展性层面，轻量级重哈希机制支持哈希桶的无缝扩展，适配数据规模增长的需求。

最终，HotRing 在高度倾斜的工作负载下，相比传统内存 KVS 显著降低了热点数据的访问延迟，提升了系统的吞吐量和可靠性，为解决热点倾斜场景下的 KVS 性能问题提供了高效的解决方案。
